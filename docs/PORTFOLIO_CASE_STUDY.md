# BizPilot AI — Portfolio Case Study

> Честный разбор проекта: что реализовано, какие решения приняты и что осталось
> непроверенным. Документ не содержит выдуманных KPI, пользовательских метрик или
> заявлений о production-эксплуатации.

## Project Overview

BizPilot AI — CRM-рабочее пространство для заявок (Leads), контактов (Contacts) и
задач (Tasks) с AI-анализом входящих обращений и опциональной автоматизацией
n8n/Telegram.

| Параметр | Факт |
| --- | --- |
| Тип | Портфолио-проект, полноценное приложение (не макет) |
| Роль | Проектирование и реализация: архитектура, backend, UI, тесты, документация |
| Статус MVP | Фактически single-tenant; multi-tenancy — цель развития, не заявленная готовность |
| Стек | Next.js 15 App Router, React 19, TypeScript 5.9 (strict), Tailwind CSS, PostgreSQL 16, Prisma 6, Auth.js 5 beta |
| Проверки текущей ревизии | typecheck, lint, unit 271/271, integration 49/49, E2E 12/12, build — PASS (2026-11-23, изолированный PostgreSQL 16) |
| Ограничения | MANAGER allow/deny не покрыт E2E; visual checklist не подписан; реальный n8n/Telegram и Docker Compose — BLOCKED |

Проект демонстрирует не только пользовательские экраны, но и инженерные решения:
слоистую архитектуру, workspace-scoped доступ, human-in-the-loop AI, outbox с
идемпотентностью и проверяемую документацию.

## Problem & Solution

**Проблема.** Небольшая команда ведёт заявки в таблицах, почте и мессенджерах.
Контекст обращения, ответственный и следующий шаг оказываются в разных местах:
заявки теряются, контакты дублируются, а руководитель не видит объективную картину.

**Решение.** Единое рабочее пространство, где заявка связана с контактом и
задачей, а AI помогает разобрать текст обращения: категория, намерение,
приоритет, оценка лида, риски, недостающая информация и черновик ответа.
Ключевой принцип — **человек принимает решение**: AI сохраняет анализ отдельно,
а бизнес-поля заявки меняются только после явного подтверждения.

**Ценность для пользователя.**

- меньше ручного разбора входящих текстов;
- прозрачная воронка и метрики на данных PostgreSQL;
- предсказуемый следующий шаг у каждой заявки;
- безопасная основа для роста: роли, workspace-scope, валидация, HMAC.

## Key Features

- Авторизация Auth.js с ролями `ADMIN`, `MANAGER`, `OPERATOR`.
- CRUD заявок, контактов и задач: поиск, фильтры, сортировка и серверная
  пагинация.
- Dashboard: KPI, воронка по статусам, 14-дневная динамика, приоритетные заявки и
  задачи, требующие внимания. Отдельной страницы Analytics нет — аналитика
  встроена в Dashboard.
- AI Assistant: анализ текста заявки, оценка лида, риски, извлечённые контакты,
  черновик ответа, история анализов.
- Явное применение AI-результата отдельным действием.
- Связи заявка ↔ контакт ↔ задача и ActivityLog.
- Опциональная автоматизация: outbox-событие `lead.created`, HMAC-подписанный
  webhook в n8n, callback, retry, идемпотентность, журнал в Settings.
- Состояния UI: loading/skeleton, empty, error, success, disabled, permission
  denied; адаптивная навигация и таблицы.
- Docker Compose (app + PostgreSQL) и отдельный profile для n8n; CI workflows.

## Technical Architecture

Три слоя без отдельного `domain/`:

1. **Presentation** — `app/`, `components/`. Server Components читают данные через
   сервисы; клиентские компоненты отвечают за взаимодействие.
2. **Application** — `services/`: бизнес-правила, workspace scope, транзакции,
   типизированные результаты.
3. **Infrastructure** — `lib/` и Prisma: БД, auth, AI-адаптер, интеграции,
   безопасность, утилиты.

Ключевые решения:

- Route Handlers выполняют транспортную работу (Origin, лимиты, Zod, auth/role) и
  вызывают сервис; бизнес-логика в них не живёт.
- `workspaceId` берётся из пользователя, загруженного из БД, а не из запроса
  клиента.
- Prisma — единственный путь к бизнес-таблицам; raw SQL только параметризованный
  и только там, где нужен (агрегации Dashboard, atomic outbox claim).
- Lead и `AutomationEvent(PENDING)` создаются в одной транзакции; dispatcher —
  best-effort ускоритель, надёжность обеспечивает PostgreSQL lease.
- AI, n8n и Telegram изолированы адаптерами; замена провайдера не меняет
  бизнес-логику.

## AI Integration

- Провайдер — OpenAI-compatible endpoint; ключи только server-side.
- Ответ модели валидируется Zod: enum-поля, диапазоны score, длины summary и
  draft reply.
- `extractedContacts` принимаются только если значения подтверждаются исходным
  текстом; контакты не выдумываются.
- AI не получает инструменты и не выполняет действий; анализ хранится в
  `AIAnalysis`, raw prompt/response не сохраняются.
- Применение результата — отдельный подтверждённый вызов, который проверяет
  принадлежность анализа заявке и workspace.
- Mock-провайдер допустим только в разработке/тестах (`ALLOW_MOCK_AI=true`); в
  production запрещён.
- Исторически реальный провайдер проверен (2026-11-20); в текущей ревизии AI не
  вызывался, внешние credentials не использовались.

## UI/UX Decisions

- Направление — Premium Intelligent SaaS, light-first: светлый canvas, navy/
  graphite текст, сдержанные синие акценты, семантические статусы.
- Executive Glass применяется точечно: границы, мягкие тени, лёгкое стекло на
  контролах; читаемость важнее декоративности.
- Иерархия: заголовок страницы → KPI/действия → основная плотность данных;
  компактные таблицы и понятные фильтры.
- Иконки Lucide; декоративные emoji не используются.
- Обязательные состояния: skeleton, empty, error, success, disabled,
  permission denied; опасные действия требуют подтверждения.
- Доступность: семантические заголовки, `aria-*`, sr-only таблица для графика,
  клавиатурный фокус.
- Адаптивность: sidebar/drawer, мобильная навигация, таблицы и карточки
  сохраняют работоспособность.
- Визуальный слой не меняет бизнес-логику; данные приходят из сервисов.

## Security Considerations

- Идентичность и workspace — только из серверной сессии; клиентские `workspaceId`,
  роль и владелец игнорируются.
- Каждый сервисный запрос и мутация ограничены текущим workspace; связанные
  сущности проверяются на принадлежность до записи.
- Роли проверяются на сервере; скрытие кнопки в UI не является защитой.
- Zod-валидация body/query/params, AI-ответов и webhook payload.
- CSRF/Origin-проверки, rate limiting, лимиты размера тела, безопасные ошибки без
  stack trace/SQL/секретов.
- HMAC-SHA256 + timestamp ±5 минут + constant-time compare в обе стороны;
  идемпотентность и replay protection.
- Секреты только в ENV/credentials; `.env` в `.gitignore`; в Git — только
  примеры без значений.
- Исторический security review (2026-11-20/21): `pnpm audit --prod` — 0 известных
  уязвимостей, gitleaks — 0 находок, IDOR/BOLA и role bypass покрыты тестами.
- Известные ограничения: фактически single-tenant, in-memory rate limit, JWT без
  отзыва сессий, hard delete. Полная multi-tenancy не заявляется.

| Integration | 49/49 в 7 файлах на изолированном PostgreSQL 16 (2026-11-23) |
| E2E | 12/12 сценариев, mock AI, собственный server Playwright (2026-11-23) |
| Workspace audit | 0 cross-workspace / 0 missing на seeded БД |
| Реальный AI smoke | Исторически PASS; в прогоне 2026-11-23 использовался mock AI |
| Visual run | 40 screenshots (10 страниц × 1440/1280/768/375), 0 overflow, 0 console errors |
| Runtime smoke | PASS: production-сервер, `/login` и `/api/ai/health` — `200` |

Все проверки выше выполнены на физически отдельном временном кластере
PostgreSQL 16 (`127.0.0.1:55432`, БД `bizpilot_phase1_test`), поднятом из
локальных бинарников без Docker. Основная служба `5432` и `.env` не
использовались, кластер после прогона остановлен и удалён.

Первый integration-прогон дал транзиентный сбой (три FK-ошибки при параллельных
insert и одна ошибка соединения); следующие два прогона подряд прошли 49/49 и
вернули БД ровно к seed. Сбой не воспроизведён и вынесен в риски, а не скрыт.

Что остаётся непроверенным: MANAGER allow/deny (в 12 E2E только ADMIN и
OPERATOR), подпись визуального checklist, реальный n8n/Telegram runtime и
Docker Compose. Поэтому полный приёмочный PASS не заявляется.

## Challenges & Solutions

1. **AI мог выдумывать контакты.** Решение: Zod-схема плюс проверка каждого
   извлечённого email/phone на присутствие в исходном тексте; иначе контакт не
   принимается.
2. **AI не должен менять бизнес-данные.** Анализ пишется в отдельную сущность;
   применение — явная транзакция после подтверждения пользователем.
3. **Изоляция workspace при исторических связях.** Read-path фильтрует связи по
   workspace; удаление заявки с чужой legacy-задачей отклоняется с 409 до любых
   изменений.
4. **Eventual-доставка без фонового воркера.** Outbox в PostgreSQL + lazy
   dispatcher + lease; при отсутствии трафика события задерживаются, и это явно
   задокументировано, а не выдаётся за exactly-once.
5. **Границы 14-дневного тренда зависели от timezone сессии.** Окно построено на
   UTC wall clock через `make_timestamp`, без неявного `timestamptz`.
6. **Риск показа реальных данных в портфолио.** Введён privacy gate: локальная
   dev-БД содержит записи сверх seed, поэтому она не использовалась. Для
   визуального прогона поднята отдельная seeded БД ровно с 1/3/10/20/15/2
   демонстрационными записями; скриншоты сняты только с неё.
7. **Beta-зависимости.** Auth.js v5 существует только в beta; версия зафиксирована
   точно, риск и путь обновления описаны.

## Final Result

**Классификация: PORTFOLIO READY WITH LIMITATIONS.**

Что готово:

- реализованное приложение с современным стеком и слоистой архитектурой;
- AI human-in-the-loop с валидацией и подтверждением;
- workspace-scoped сервисы, роли и защита webhook;
- документация: архитектура, API, security, deployment, n8n, demo, этот case study;
- проверки 2026-11-23 на изолированной БД: typecheck, lint, unit 271/271,
  integration 49/49, E2E 12/12, build, аудит 0 и 40 screenshots без overflow и
  console errors.

Почему не полный PORTFOLIO READY:

- MANAGER allow/deny не покрыт E2E: в наборе только ADMIN и OPERATOR, поэтому
  роль MANAGER проверена лишь статически.
- Визуальный checklist не подписан пользователем; автоматические проверки
  responsive не заменяют визуальный review.
- Первый integration-прогон дал транзиентный сбой, который не воспроизвёлся;
  flaky-риск остаётся под наблюдением.
- Реальный n8n/Telegram runtime не проверен; workflow — draft.
- Docker Compose локально не проверялся; multi-tenancy не реализована.

Почему не NOT READY: приложение собирается и запускается, ключевые проверки
текущей ревизии пройдены, код и документация согласованы, а ограничения
перечислены явно, без подмены фактов.
